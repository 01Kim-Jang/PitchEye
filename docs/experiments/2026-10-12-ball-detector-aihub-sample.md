# 공 검출 모델 첫 학습 (AI Hub 경량 샘플)

- 날짜: 2026-10-12
- 코드: `ml/aihub.py`, `ml/ball_model.py`, `ml/train_ball.py`
- 목적: **학습 파이프라인(라벨 읽기 → 학습 → 평가)이 끝까지 도는지 확인.** 쓸 만한 모델을 만드는 것이 목적이 아니다.

> 아래 수치는 AI Hub 샘플에서 잰 것이며 **PitchEye의 정확도가 아니다.**
> 카메라 구도, 프레임레이트(120fps), 경기 수준이 우리 조건과 다르다.

## 데이터
본 실험은 한국지능정보사회진흥원(NIA) AI Hub의 「야구 주요 규칙 판정 영상 데이터」(dataSetSn=71726) 경량 샘플을 사용했다.
데이터와 학습된 가중치는 저장소에 올리지 않는다(재배포 금지, `data/raw/`·`ml/runs/`는 git 제외).

| 항목 | 값 |
|---|---|
| 이미지 | 1,390장 (1920×1080), 라벨 JSON 1,390개 |
| 상황 | 스트라익_볼 320, 세이프_아웃 394, 파울_페어 384, 파울헛스윙 292 |
| 공 박스 | 1,001개 (공이 없는 이미지 389장) |
| 공 크기(긴 변, px) 중앙값 | 스트라익_볼 14, 파울_페어 15, 세이프_아웃 19, 파울헛스윙 22 |
| 촬영 단위 | 158개. 프레임은 연속이 아니라 띄엄띄엄 뽑힌 것 |

함께 받은 「스포츠 영상 데이터(야구)」(dataSetSn=488) 샘플은 **공 라벨이 없어** 쓰지 않았다.
샘플 1,925장은 모두 "야수 송구" 장면이고 사람 박스와 키포인트만 있다.

## 방법
- 모델: ResNet-18 앞부분(1/8 해상도까지, ImageNet 사전학습) + 작은 디코더. 공 중심을 1/2 해상도 히트맵으로 출력. 가중치 파일 약 3.4MB.
- 박스 검출기 대신 히트맵을 쓴 이유: 공이 10~20px로 작고, 궤적 계산에는 중심점만 필요하다.
- 학습: 원본 해상도에서 320×320 조각을 잘라 학습(전체를 줄이면 공이 사라진다). 좌우 반전, 밝기·대비 변화. 20에폭, AdamW, Apple M1(MPS)에서 약 17분.
- 분할: 학습 1,181장 / 검증 209장. **촬영 단위로 나눠** 같은 투구를 다른 카메라로 찍은 장면이 양쪽에 섞이지 않게 했다.
- 평가: 1920×1080 전체 이미지에서 봉우리를 찾고, 공 중심에서 max(8px, 공 크기) 안에 있으면 찾은 것으로 본다.

## 해석
- **파이프라인은 동작한다.** 라벨 읽기, 학습, 전체 이미지 평가가 끝까지 돈다.
- **작은 공에서 무너진다.** 10px 미만은 26개 중 10개만 찾았다. 우리 조건(약 19px, 추정)은 10~20px 구간에 해당하는데 여기도 60개 중 40개다.
- **한 장만 보고 찾는 방식의 한계가 보인다.** 임계값을 낮추면 공이 아닌 것을 많이 집는다. 흰 선, 베이스, 유니폼 같은 것이 공과 비슷하게 보이기 때문으로 추정한다(확인하지 않음).
- 손실이 20에폭째에도 줄고 있었다. 학습이 덜 된 상태다.
- 임계값별 수치는 같은 검증 데이터에서 본 것이라, 여기서 임계값을 고르면 낙관적이다.

## 이 결과로 말할 수 없는 것
- 스트라익_볼 검증 이미지는 16장뿐이다(공 있는 것 13장). 이 구간 수치는 **표본이 너무 작아 의미를 두기 어렵다.**
- 전체 검증도 209장이다. 몇 %p 차이는 우연일 수 있다.
- 백네트 뒤 3m 구도, 240fps, 사회인야구 환경에서의 성능은 이 실험으로 알 수 없다.
- 포수·심판에 가려진 공에 대한 성능은 재지 않았다.

## v1: 같은 데이터로 개선 시도 (2026-10-13)

v0의 문제(학습 부족, 작은 공, 오검출)를 보고 세 가지를 바꿨다. 검증 데이터와 평가 방법은 v0와 같다.

| 바꾼 것 | v0 | v1 |
|---|---|---|
| 학습량 | 20에폭 (약 1,500스텝, 17분) | 100에폭 (약 7,300스텝, 29분) |
| 조각 크기 | 320px | 192px (한 스텝이 빨라진다) |
| 크기 변화 증강 | 없음 | 0.6~1.4배 |
| 공 없는 조각 비율 | 20% | 40% |
| 모델 | 1/8 해상도까지 | 1/16 해상도(문맥) 단계 추가 |
| 가중치 크기 | 3.4MB | 13.5MB |

### 결과

| 지표 | v0 | v1 |
|---|---|---|
| 가장 센 봉우리가 공인 비율 | 75.4% (101/134) | **80.6% (108/134)** |
| 중심 오차 중앙값 (임계값 0.5) | 1.41px | 1.12px |

같은 임계값에서는 찾는 비율이 오르고 오검출도 늘었다. v1이 전반적으로 더 높은 점수를 내기 때문이다.

| 임계값 | 찾은 비율 v0 → v1 | 봉우리 중 진짜 공 v0 → v1 | 공 없는 이미지 오검출 v0 → v1 (75장 중) |
|---|---|---|---|
| 0.3 | 69.4% → 79.9% | 61.2% → 46.9% | 11 → 30 |
| 0.5 | 61.9% → 73.1% | 88.3% → 84.5% | 3 → 5 |
| 0.7 | 52.2% → 61.2% | 98.6% → 95.3% | 0 → 1 |

임계값을 달리해 **찾은 비율이 비슷한 지점끼리** 비교하면 v1이 낫다.

| 비교 지점 | 찾은 비율 | 봉우리 중 진짜 공 |
|---|---|---|
| v0 (임계값 0.3) | 69.4% | 61.2% |
| v1 (임계값 0.5) | 73.1% | 84.5% |
| v0 (임계값 0.5) | 61.9% | 88.3% |
| v1 (임계값 0.7) | 61.2% | 95.3% |

공 크기별 찾은 수 (임계값 0.5):

| 공 크기 | v0 | v1 |
|---|---|---|
| 10px 미만 | 5 / 26 | **17 / 26** |
| 10~20px | 37 / 60 | 39 / 60 |
| 20px 초과 | 41 / 48 | 42 / 48 |

### 해석
- **작은 공이 가장 크게 나아졌다** (10px 미만 5/26 → 17/26). 크기 변화 증강과 학습량 증가의 효과로 보인다. 어느 쪽 덕인지는 따로 떼어 실험하지 않아 알 수 없다.
- **우리 조건에 해당하는 10~20px 구간은 거의 그대로다** (37/60 → 39/60). 이 구간이 여전히 약점이다.
- 가장 센 봉우리 기준으로는 7장이 더 맞았다(101 → 108). 검증이 134장이라 이 정도 차이는 우연일 가능성을 배제할 수 없다.
- 문맥 단계를 넣었지만 오검출이 줄었다는 증거는 없다. 같은 임계값에서는 오히려 늘었다.
- 세이프_아웃 상황은 여전히 나쁘다 (가장 센 봉우리 기준 55.9%). 공이 글러브·선수 근처에 있는 장면이 많아서로 추정한다.
- v0와 v1 모두 같은 검증 데이터를 보고 설정을 골랐다. 별도의 시험용 데이터가 없으므로 이 비교 자체가 낙관적일 수 있다.

**결론: 같은 데이터에서 개선은 있었지만 크지 않다. 한 장만 보는 방식과 공 1,000개 규모의 데이터로는 여기가 한계에 가깝다고 본다.**

## 다음
1. **연속 프레임 활용**: 고정 카메라에서 공은 움직이고 배경은 가만히 있다. 앞뒤 프레임을 함께 넣거나 프레임 차이를 쓰면 오검출이 크게 줄 것으로 기대한다. 이 샘플은 프레임이 띄엄띄엄이라 시험할 수 없고, 직접 촬영한 영상이나 전체 데이터가 필요하다.
2. **직접 촬영한 240fps 영상**으로 추가 학습과 평가. 최종 수치는 이 영상으로만 낸다.
3. 전체 데이터(스트라익_볼 13만 건)를 쓰려면 용량과 이용 조건을 먼저 확인한다.
4. 히트맵 해상도를 원본과 같게 하는 것은 그다음이다.
